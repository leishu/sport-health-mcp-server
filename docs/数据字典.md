# 健康数据字典

> 本文档由 `data/sport-health.db` 的实际结构导出（表名、字段名、类型、行数均取自库），
> 字段含义为人工维护。数据库结构版本见 `PRAGMA user_version` = 8。

## 一、数据来源

### pm2 / bpm2 的字段语义（实测确认）

`pm2`（与等价的 `p-m`）是**华为官方单公里分段配速**，`get_run_splits` 用它做 `vendorSplits`：

| 字段 | 含义 |
| --- | --- |
| `d` | 该段**终点**的累计距离（米），逐行递增；末段不足 1000 米时为实际总距离 |
| `n` | 该段终点处的轨迹点序号 |
| `p` | 该段**配速**（秒/公里）；整公里段时数值上等于该段用时秒数 |

一行形如 `tp=pm2;d=2000;n=349;p=346.0;`，含义是「到 2 公里为止，本公里用了 346 秒」。
整公里段的 `p` 相加约等于该次运动的总时长（样本 `hw-20251115-1726-134`：5 段合计 1798.9 秒，
总时长 1804.7 秒），末段的 `p` 仍是配速而非用时，按 `p × 段距离` 折算才是用时。

`bpm2`（等价 `b-p-m`）是**华为官方单英里分段配速**（英制口径，对应 summaryData 里的
`britishPaceMap`），字段含义与 `pm2` 一一对应，只是距离单位换成英里：

| 字段 | 含义 |
| --- | --- |
| `d` | 该段**终点**的累计距离，单位是**千分之一英里**（1000 = 1 英里 = 1609.344 米）；末段不足一英里时为实际总距离 |
| `n` | 该段终点处的轨迹点序号（与 `pm2` 的 `n` 不是同一个位置，因为切分点不同） |
| `p` | 该段**配速**（秒/英里）；整英里段时等于该段用时秒数 |

早前把它记成「与 pm2 恒差 204~224 秒的未知量」，那是把两种切分的第 i 段硬减出来的假象：
一英里里既有整公里也有不足一公里的部分，差值自然随配速变化。三项实测都对得上：

- 用 `pm2` 的分段配速反推每英里用时，与 `bpm2` 的 `p` 中位差 **0.57 秒**（851 段，76.5% 在 5 秒内）；
- `bpm2` 末段 `d` 换算成米 vs 运动总距离，173 条记录比值中位数 **1.0000**（P5 0.9998 / P95 1.0010）；
- 行数与 `pm2` 的比例 926 / 1472 = 0.629，与 1/1.609 一致。

`britishPartTimeMap` 是它的逐段累加，`partTimeMap` 则是 `pm2` 的累加。MCP 工具里
`get_official_splits` 的 `unit=mile` 就用这套口径，`unit=km` 用 `pm2`。

### rs / 其它流的数值口径（实测）

| 类型 | 实测结论 |
| --- | --- |
| `rs` | `k` 是轨迹点序号（不是时间），`v` 的单位约 **0.1 m/s**：`v × 0.36` 得到的 km/h 与 `run_activity.avg_speed_kmh` 之比，173 条带该流的记录中位数 0.999、区间 0.75~1.01。`get_run_streams` 直接给出换算后的 `speedKmh` / `paceText` |
| `rp` | 跑姿：`gct` 触地时间(ms)、`vo` 垂直振幅(cm)、`gtb` 左右平衡(%)、`ee`/`sa`/`fsp` 等恒为 `-1`/`-101`（该机型未采集或未接跑步动态传感器）。63 条记录有，数值范围 `gct` 0~321、`vo` 0~10.5、`gtb` 0~51.9 |
| `pad` / `scp` | 按毫秒时间戳采样，`v` 分别在 0~38、0~176 之间，语义未确认，未参与任何分析 |
| `i-h-r` | 「瞬时心率」采集，270 行里 239 行 `v=-1`（未采集），有效值 0~136 bpm，**不能当作逐点心率**（逐点心率在 `track_point.heart_rate`） |
| `evt` | `e` 恒为 0，`ty` 取 0/1（各有 97 行，疑似开始/结束），`st` 是毫秒时间戳 |

### 与 summaryData 的对应关系

`summaryData.paceMap` / `britishPaceMap` 是这段流的汇总形态，键的拼法相同，都是
「距离 × 10000 + 轨迹点序号」，但**距离单位不同**：`paceMap` 是米（`10000165` = 1 公里处、第 165 点），
`britishPaceMap` 是千分之一英里（`10000280` = 1 英里处、第 280 点）。

| summaryData | track_stream | 说明 |
| --- | --- | --- |
| `paceMap` | `pm2` | 逐段数值完全相同（秒/公里）；`partTimeMap` 是它的逐段累加 |
| `britishPaceMap` | `bpm2` | 逐段数值完全相同（秒/英里）；`britishPartTimeMap` 是它的累加 |
| `mExtendTrackDataMap.temperature` 等 | — | 手机自报天气，可与 `run_weather` 回填值对照 |

MCP 工具 `get_run_streams` 读这张表；`get_run_summary_data` 读 `summaryData`（只把 `paceMap`
拆成 `kmSplits`，`britishPaceMap` 原样保留并提示走 `get_official_splits`）；`get_official_splits`
把两者分别按公里 / 英里口径与 GPS 分段逐段对比。

| `user_run_level_json` | TEXT | 是 | `userRunLevel` 原始 JSON |
| `motion_path_run_level_json` | TEXT | 是 | `motionPathRunLevel` 原始 JSON |

读数入口是 `get_run_level` 工具（`predict_race_time(includeOfficial=true)` 也会读同一个快照做对照）：

- `record_day` 是华为导出原文 `yyyyMMdd`，主键；`RunLevelStore` 解析时兼容 ISO 日期，读不出来的行直接跳过。
- 五档速度单位是 **km/h**，不是配速。工具层按 `3600 / 速度` 换算成秒/公里，再格式化成 `4'35"/km`；
  库里保持原文，避免派生表重建时出现二次换算误差。
- 成绩列是「官方给这个距离的成绩」，单位秒。超过 1 小时的成绩（半马/全马）在工具层用 `H:MM:SS`
  输出，`PaceFormat.duration` 会丢掉秒，不要用它渲染成绩。
- 五档字母沿用华为叫法：A 有氧耐力、E 轻松跑、I 间歇跑、M 马拉松配速、R 重复跑。
  `user_run_level_json` 里还有 `tSpeed`（乳酸阈），当前没有拆列，需要时再解析原始 JSON。

```sql
-- 每个月的跑量与平均配速
SELECT substr(run_date,1,7) AS month, COUNT(*) runs,
       ROUND(SUM(distance_meters)/1000.0,1) km,
       ROUND(AVG(avg_pace_seconds)) pace_s_per_km
FROM run_activity WHERE sport_family='RUN' GROUP BY month ORDER BY month;

-- 一次跑步的配速与心率
SELECT substr(t.timestamp,12,5) t, ROUND(t.distance_meters)/1000.0 km, t.heart_rate, t.cadence
FROM track_point t WHERE t.run_id='hw-20261107-0653-12267' ORDER BY t.seq;

-- 最近 30 天静息心率与 HRV
SELECT substr(start_time,1,10) d, metric_key, value_num, value_text
FROM health_metric
WHERE metric_key IN ('RESTING_HEART_RATE','HEART_RATE_VARIABILITY')
  AND start_time >= date('now','-30 day') ORDER BY start_time;

-- 每天步数：直接查派生表，不用再按 sport_type 去重
SELECT activity_date, steps, walk_steps, run_steps, ROUND(distance_meters/1000.0,2) km,
       active_minutes, stand_minutes
FROM daily_activity ORDER BY activity_date DESC LIMIT 30;

-- 体重趋势：只取自己的那台秤配置（gender=1、height 186），避开同秤上其他人的记录
SELECT substr(measured_at,1,10) d, weight_kg, bmi, body_fat_percent, muscle_mass_kg
FROM body_measurement
WHERE gender = 1 AND height_cm = 186 AND has_body_composition = 1
ORDER BY measured_at DESC LIMIT 20;

-- 最近两周的睡眠（只看夜睡，午睡单列一步）
-- 极少数日期会有两段夜睡（如 2026-01-11），要「一天一行」就先按 sleep_date 取最长的一段
SELECT sleep_date, substr(session_start,12,5) bed, substr(session_end,12,5) wake,
       ROUND(asleep_minutes/60.0,1) h, deep_minutes, rem_minutes, awake_minutes
FROM sleep_session WHERE sleep_type = 'NIGHT' ORDER BY sleep_date DESC LIMIT 14;

-- 睡眠时序（按段算时长）
SELECT start_time, metric_key, (julianday(end_time)-julianday(start_time))*24*60 minutes
FROM health_metric WHERE metric_key LIKE 'PROFESSIONAL_SLEEP_%'
ORDER BY start_time DESC LIMIT 20;

-- 一天的全景：步数 + 睡眠 + 静息心率 + 压力（四张派生表按日期对齐）

       v.resting_heart_rate, v.hrv_rmssd, v.stress_avg
FROM daily_activity a
LEFT JOIN daily_vitals v ON v.heart_date = a.activity_date
LEFT JOIN sleep_session s ON s.sleep_date = a.activity_date AND s.sleep_type = 'NIGHT'
ORDER BY a.activity_date DESC LIMIT 30;

SELECT sleep_date, sleep_score, sleep_efficiency, avg_heartrate, avg_hrv,
       avg_oxygen_saturation, rdi, snore_freq
FROM sleep_report ORDER BY sleep_date DESC LIMIT 14;

-- 某次跑步的跑姿流（gct 触地时间、vo 垂直振幅、gtb 触地平衡…）
SELECT seq, point_index,
       json_extract(data,'$.gct') gct_ms,
       json_extract(data,'$.vo')  vertical_oscillation,
       json_extract(data,'$.gtb') ground_time_balance
FROM track_stream
WHERE run_id = 'hw-20261107-0653-12267' AND stream_type = 'rp'
ORDER BY seq LIMIT 50;

-- 每 5 秒速度流（做配速波动、分段分析用）

ORDER BY seq;

-- 华为官方单公里配速（pm2：d 是累计距离，value/p 是该段配速，秒/公里）

FROM track_stream

SELECT source_file, row_number, row_data
```

## 五、口径与坑

1. **坐标系**：华为 JSON 导出是 GCJ-02，TCX 是 WGS-84，两者同一次跑步（10-25，都是 7123 米）
   起点相差约 540 米。导入时 JSON 坐标已统一转成 WGS-84，库里只有一套坐标系。
2. **重复副本**：同一份数据会同时以手机端与健康平台两种 `type` 出现，`recordId` 与采样时刻完全相同。
   导入时统一规范键：`DATA_POINT_DYNAMIC_HEARTRATE` → `DYNAMIC_HEART_RATE`、`STRESS_DATA` → `STRESS`、
   `DATA_POINT_REST_HEARTRATE` / `DATA_POINT_NEW_REST_HEARTRATE` → `RESTING_HEART_RATE`，
   再由主键 `(record_id, metric_key, start_time)` 吃掉重复：117 万条采样点去重后剩 81.9 万条。
3. **同一次跑步只留一条**：10-25 ~ 11-04 的 6 次跑步 TCX 与 JSON 两边都有，按开始时刻相差 2 分钟内判定为同一次。
   现在由 **JSON 接管**：它是 TCX 的超集（多出心率、步频、步数、热量），接管时删掉 TCX 的 `run_activity` 与 `track_point`、
   清掉 TCX 指纹（下次同步会让 TCX 重新走到「让位」分支，不重复写），天气行改挂到新 id 上。
   所以这 6 次现在 id 形如 `hw-20261025-0656-11136`、轨迹点全部带心率，库里已没有 `source_kind='tcx'` 的行。
   反向也能退：库里的 `hw-` 行不存在时（例如 JSON 那边删掉了这次运动），TCX 会重新写入一条无心率记录。
4. **丢失定位**：华为用 `lat=90; lon=-80` 表示此刻无定位，导入时已丢弃，不入 `track_point`。
5. **单位**：依据导出包里的 `Data Field Description.xlsx`——时间戳、`totalTime` 是毫秒，
   `totalDistance` / `distance` 是米，`totalCalories` / `calorie` 是**卡（cal）**，
   `mTotalDescent` / `creepingWave` 是**分米**。落库时统一换成秒 / 米 / 千卡（cal ÷ 1000、分米 ÷ 10）。
   个别记录的汇总下降与轨迹高度自相矛盾（如 `hw-20260803-1048-4245`：下降 1,611 米，
   但 min/max 高度只差 295 米），用之前建议先跟 `min_altitude_meters` / `max_altitude_meters` 对一下。
6. **每分钟去重**：手机与手表会各自上报同一分钟（同一 `start_time + sport_type`），
   `activity_minute` 只保留步数较大的那条，否则一天步数会翻倍。原始 10.7 万行 → 7.05 万行。
   注意去重键包含 `sport_type`，同一分钟仍可能同时存在「走路」和「跑步」两条（约 2,200 组）；
   按天汇总与华为自报步数基本一致，按类型汇总会偏大。
7. **步频稀疏**：`s-r` 采样约 40 秒一个，轨迹点上按 120 秒容差匹配，超出容差为 NULL，不做外推。
8. **只有 RUN 进快照**：`JdbcHealthDataRepository` 只加载 `sport_family='RUN'`，
   步行与其它运动仍在库里（`run_activity` 190 行），但不会污染跑量、个人最佳等统计。
9. **天气覆盖率与口径**：`run_weather` 190 行，其中 `sport_family='RUN'` 的 154 条跑步里
   151 条 `OK`、3 条 `FAILED`（2026-11-04 / 11-07 / 11-09，都是 open-meteo 读超时），
   0 条 `UNAVAILABLE`；剩下的 36 行是步行与其它运动的天气（`WALK` 19 条 `OK`、
   `OTHER` 17 条 `UNAVAILABLE`，后者室内运动没有有效坐标）。**统计口径只算 `RUN`**：
   `RunWeatherStore.pending()` 与 `stats()` 都带 `sport_family = 'RUN'`，所以
   「总跑步数」= 154，与 `describe_data_source.runningCount` 一致；旧版统计用
   `COUNT(*) FROM run_activity`（=190）当分母，覆盖率会凭空少 19%。
   失败行默认冷却 7 天（`retry-failed-after-days`）才会重试，想立刻补用 `sync_weather`
   （默认忽略冷却），只想同步数据不想等网络用 `reload_data(weather=false)`。
   做天气分析前先按 `status='OK'` 过滤，或用 `get_weather_impact` 的 `weatherCoverage` 看缺口。
10. **字典里有保留组合**：`health_metric_type` 中有 6 个 `type_code + metric_key` 当前没有数据
    （7 的 RESTING_HEART_RATE，以及 10002、10006、400021、500023、500026），
    它们是跨副本去重后可能出现的「另一种写法」，反向查询（从字典看数据）时用 LEFT JOIN。
11. **派生表什么时候更新**：结构升到 v8 的那一次同步会无条件回填 12 张派生表
    （v7 的 4 张 + v8 新增的 `sleep_report`、`ecg_record`、`daily_sport_stat`、
    `sport_daily_dimen_stat`、`daily_health_stat`、`daily_health_samplestat`、`run_level`、`medal`）；
    之后只在「本次真的有文件重导」时才重建。空转的同步（文件全部指纹命中）不会重算，
    所以手工改过原始表之后要等一次真正的重导，或者一次性 `DELETE FROM` 派生表
    让下一次同步认为「表空了」而强制回填。重建全量约 5.4 秒（17.8 万条睡眠分期窗口函数
    + 5,008 行 Excel 聚合）。
12. **体重混着别人的数据**：同一台体脂秤上配了多个用户，308 条记录里至少有
    gender=1/186 cm（141 条，71.2–76.5 kg）、gender=0/168 cm（132 条，67.3–71.5 kg）、
    gender=0/171 cm（25 条，55.9–58.5 kg）、gender=1/193 cm（3 条，85.3 kg）四套配置，
    还有 7 条没配性别身高。直接 `MIN/MAX(weight_kg)` 会得到 55.9~85.3 这种无意义的区间，
    做趋势必须按 `gender + height_cm` 过滤；`has_body_composition=0` 的 166 条只有体重，
    体脂率相关列全是 NULL。
13. **午睡不等于「下午睡的」**：`sleep_type='NAP'` 只说明这段会话的全部时长都记在
    `PROFESSIONAL_SLEEP_NOON` 分期里。150 段里有 16 段是从 21:00~01:00 开始的深夜小睡，
    最长一段 `asleep_minutes` 达 697 分钟（`in_bed_minutes` 1,154 分钟，明显异常）。
    要看真正的午休，再加 `substr(session_start,12,2) BETWEEN '11' AND '15'`。
14. **动态心率是采样不是极值**：`min_heart_rate` / `max_heart_rate` 来自逐分钟自动采样
    （一天 200~320 条，睡眠时会掉到 37~40，跑步时会冲到 140+），不能当成医学极值；
    想要运动心率看 `track_point.heart_rate` 或 `run_activity.avg_heart_rate`。
    静息心率同理，一天多条取最小值，且 468 天里有 100 天没有采样（没戴表）。
15. **sleep_report 的时间字段是原始值**：`bed_time` / `fall_asleep_time` / `rising_time` /
    `wakeup_time` / `prepare_sleep_time` 是华为 `summaryData` 里的原始数值（秒级 epoch），
    没有换算成本地文本；要按日期对齐请用 `sleep_date`、`start_time`、`end_time`，
    要精确到时刻请自行 `datetime(bed_time, 'unixepoch')` 并按 `time_zone` 修正。
16. **Excel 清洗规则**：华为把 JSON 列存成 `"\t[{""a"":1}]"` 这种「前导 Tab + 外层引号 +
    双引号转义」形态。导入时统一 `strip()`、去掉成对外层引号、把 `""` 还原成 `"`，再去一次空白。
    所以 `excel_sheet_row.row_data` 里的值已经是可 `json_extract` 的干净文本；空单元格不写入对象。
    例外是 `daily_health_stat.total_info` 里 type=12 的 `intensityMap`：源数据本身用
    `{1:108,2:4}` 这种无引号键，**364 行不是合法 JSON**，`json_valid()` 会返回 0。
    原文按原样保留，需要解析时先做正则或字符串替换，不要假定所有 `total_info` 都能 `json_extract`。
17. **原始数据已全量入库**：`sample_sequence` 11,790 条与源 JSON 的 recordId 一一对应；
    Excel 共 38 个文件、41 张非空工作表、5,008 行（SportsHealth 4,711 行 + HUAWEI_Research 297 行）。
    空表与官方字段说明文件（文件名含 `description`）被跳过；其余行均保留，
    包括看起来「只有日期、其他列全空」的行——它们同样是导出的一部分。
